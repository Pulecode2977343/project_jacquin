Gestión de Identidad y Cuentas

POST /register.php

Flujo de Registro de Usuario

Al procesar un nuevo registro, el sistema ejecuta las siguientes fases:

  1. Validación de Duplicados: Se realiza un SELECT id_usuario FROM usuarios WHERE email = ?. Si existe registro, el sistema retorna un 409 Conflict para prevenir colisión de cuentas.
  2. Criptografía: La contraseña se procesa mediante password_hash($raw, PASSWORD_BCRYPT). No existe almacenamiento de texto plano.
  3. Persistencia: Se inserta el usuario con id_rol = 3 (Estudiante) por defecto.
POST /admin_update_user_full.php

Control Total de Usuarios (Admin)

Permite la modificación de atributos sensibles que están bloqueados para el usuario común:

  • Elevación de Privilegios: Cambio directo de id_rol (ej. de Estudiante a Docente).
  • Corrección de Identidad: Edición de email y teléfono sin restricciones de validación soft.
POST /recover_request.php

Flujo de Recuperación de Contraseña

Gestión de Clases y Notas

Asignación de Profesores

POST /admin_assign_teacher.php

El administrador vincula un docente a un curso. El sistema valida:

  • Que el id_rol del usuario sea 2 (Docente).
  • Redundancia: Si el profesor ya tiene el curso asignado, el sistema actualiza el registro en lugar de duplicar, manteniendo la integridad referencial.

Control Académico (Docente)

El profesor interactúa con tres ejes lógicos:

// 1. Asistencia
INSERT INTO attendance (id_student, id_schedule, id_course, status, date) ...

// 2. Notas/Progreso
UPDATE enrollment_grades SET grade = ?, feedback = ? WHERE id_enrollment = ? ...

// 3. Consulta de Asignación y Cupos (OPTIMIZADA)
// Se eliminó el problema de N+1 consultas. Ahora se obtienen cursos, horarios 
// y docentes mediante 3 consultas SQL agrupadas, garantizando estabilidad en zrok.
SELECT c.id_course, c.course_name as name,
GROUP_CONCAT(DISTINCT u.full_name SEPARATOR ', ') as teacher_name 
FROM courses c 
LEFT JOIN schedules s ON c.id_course = s.id_course
LEFT JOIN schedule_teachers st ON s.id_schedule = st.id_schedule
LEFT JOIN usuario u ON st.id_teacher = u.id_usuario
GROUP BY c.id_course;

Gestión de Capacidad (Cupos)

Validación de Límite de Estudiantes

POST /request_enrollment.php

Antes de permitir una solicitud de inscripción, el sistema ejecuta un validador de aforo:

  1. Consulta el max_students definido en la tabla courses.
  2. Suma el total de enrollments con estado 'accepted'.
  3. Lógica de Bloqueo: Si actuales >= max_students, la API bloquea la petición y retorna un 403 Forbidden con el mensaje "Curso sin cupos disponibles".

Sistema de Inscripción e Inteligencia de Conflictos

Manejo de Redundancia en Inscripción

Si un estudiante intenta inscribirse en un curso donde ya está matriculado:

  1. El sistema detecta el registro activo en la tabla enrollments.
  2. Caso Múltiple: Si el estudiante cursa dos instrumentos diferentes (ej. Piano y Violín), se generan dos id_enrollment distintos. El sistema los maneja como instancias académicas independientes.

El Algoritmo de Traslados (Intersection) - Docentes y Alumnos

Implementación en helpers/conflict_helper.php. Esta lógica es bidireccional: protege la agenda tanto del estudiante como del profesor.

Validación de Conflictos para Docentes:

// El sistema busca si el docente ya tiene otra clase en el mismo bloque
SELECT id_schedule FROM enrollment_schedules es
JOIN enrollments e ON es.id_enrollment = e.id_enrollment
JOIN courses c ON e.id_course = c.id_course
WHERE c.id_teacher = :teacher_id
AND es.day_of_week = :new_day
AND ((:new_start < es.end_time) AND (:new_end > es.start_time))

Este motor garantiza que un profesor no sea asignado a dos salones o clases diferentes si sus bloques horarios se traslapan, asegurando una logística impecable.

Mejora Reciente: Se corrigió la lógica de desvinculación asegurando que la API apunte correctamente a la columna enrollment_id para evitar fallos de integridad al eliminar registros.

Módulo de Inventario (Roadmap)

Estado Actual del Módulo

El sistema de inventario se encuentra actualmente en una etapa de transición/mejora técnica. Aunque posee una estructura CRUD funcional, el enfoque principal ha sido la estabilidad del motor académico.

Capacidades Técnicas Implementadas

GET /admin_inventory_get.php

La lógica actual permite el seguimiento básico de activos institucionales (especialmente Pianos y equipos de sonido):

  • inventory_create.php: Registro de nuevos activos con metadatos de mantenimiento.
  • inventory_update.php: Modificación del estado actual del instrumento (Disponible / En Mantenimiento / Fuera de Servicio).
Visión a Futuro: El objetivo es integrar el inventario con el sistema de horarios, permitiendo asignar automáticamente un instrumento específico (ej. Piano N°3) a un salón y docente en un bloque horario determinado.

Control Maestro (CMS)

Gestión de Hero y Eventos

El administrador puede modificar la "Identidad Visual" sin tocar código:

  • Cambio de Hero: admin_upload_hero.php procesa la imagen, valida el MIME-type (evita scripts maliciosos), la renombra y actualiza la ruta en la base de datos que el frontend consume mediante get_hero_config.php.
  • Promoción de Eventos: admin_create_event.php permite marcar un evento como "Destacado" (featured). Esto altera la posición en el Swiper.js del frontend.

Asignación de Horarios

POST /admin_assign_schedules.php

El administrador puede asignar uno o varios horarios a un solo estudiante para un mismo curso (ej. Teoría el Lunes, Práctica el Jueves). El sistema maneja esto vinculando múltiples id_schedule a un solo id_enrollment en la tabla puente enrollment_schedules.

Refinado Estético (V7): Los modales administrativos han sido actualizados con botones de cierre circulares semi-transparentes con efectos de cristal y rotación suave, alineándose al Brandbook V2.

Seguridad y Captura de Errores

Middleware de Bloqueo

Todos los archivos bajo el prefijo admin_*.php requieren la inclusión de middleware/auth_helper.php. La lógica interna es: 

if (!isset($_SESSION['user']) || $_SESSION['role'] !== 1) {
    header("HTTP/1.1 403 Forbidden");
    echo json_encode(["status" => "error", "message" => "Acceso administrativo requerido"]);
    exit;
}
